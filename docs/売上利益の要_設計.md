# 店の売上と利益の要 — 一気通貫の設計（2026-10-13 作成・2026-10-14 GitHub と照合して更新・Fable）

人（ひろき）の判断を AI に落とし込み、「何を出す → 出す → 値段 → 反応を見る → 直す・消す」の 1 周を、Shopee の全店と JOOM で同じ道具・同じ表で回すための設計。
各道具の細かい手順は各リポジトリの正本にある。ここは**全体の形と、人が決める所と、作る順番**だけを書く。変えたら同じ日にここを直す。

## 0. ゴールと考え方

- ゴール：**利益の合計を増やす**（利益率ではなく合計。2026-09-30 決定）。
- 店が強くても値段が高ければ売れない。だから要の順番は **③ 値段 → ④ 反応 → ⑤ 直す・消す → ① 何を出す → ② 出す**（2026-10-13 ひろきさん：ライバル追随と価格調節が最優先）。
- 原則（全部、ひろきさんの既決）
  1. 道具も表も**全店共通**。店の違いは「店の列」か「店ごとの設定ファイル」だけ。店ごとに別の表・別のタブ・別のスクリプトは作らない。
  2. **人が決める所は、決まった表の決まった列**にだけ書く。Claude はその表を毎回読んで動き、結果を**同じ表**か今あるモニターに書く。新しい見る場所は作らない。
  3. 人が覚える事（スキル名・定型文の名前・列の記号）を前提にしない。頼み方は日本語の一言。
  4. 店に送る前は完成形を見せて OK（新規出品・作り直し・値段の付け直し）。日々の自動の値段の上げ下げだけは、決めたルールの範囲で自動。
  5. 送った後は必ず点検（削除・BAN・順位下げ）。

## 1. 人が決める事は 7 つだけ（それ以外は Claude）

| # | 決める事 | 書く場所 | いつ |
|---|---|---|---|
| 1 | どの自店商品を、どのライバルと比べるか（ライバルの URL） | front_list（スプレッドシート「フロント商品・改善商品リスト」）の rival_url 列。**Claude が候補の行を足し、人は確定 OK を付けるだけ**にする（下の ③） | 週 1 の報告を見た時 |
| 2 | その商品をどこまで追いかけるか（下限の利益率。空欄＝0%） | front_list の「下限の利益率」列 | 同上。0% より下はここに書いた時だけ |
| 3 | 新しく出す候補を出すか出さないか | 出品待ちの表（リサーチDB に 1 タブ。全店共通。下の ①）の「人の可否」列。Shopee は当面すべて人が OK、JOOM は自動 | 週 1 の報告を見た時 |
| 4 | 売れない物を消すか | Claude が一覧を返事で見せ、OK を返す（表は作らない） | 週 1 |
| 5 | ブランド・商品のルール（この国でこのブランドは出さない、など） | 出品の道具の config/brand_policy.yaml・knowledge/restrictions.yaml（Claude が書く。人は返事で答えるだけ。同じ事を二度聞かない） | 聞かれた時 |
| 6 | 値段の基本ルール（利益率のスタート・下限・何日売れなければ下げる・手数料率） | 価格改定ツールの pricing_rules.json（Claude が書く）。見るのは価格改定モニターの「ルール」 | 変えたい時 |
| 7 | 違反の異議申し立てを送る（セラーセンターの手作業。500 文字まで） | Claude が文面と期限を返事で出し、ひろきが送る。結果は ec-knowledge の `Shopee/50_ペナルティと異議申し立て.md` に Claude が記録 | 週 1 の報告を見た時 |

## 2. 五つの段（今あるもの・足りないもの）

### ③ 値段（最優先）
**今あるもの**
- 価格改定ツール（PC で毎日）：式 ＝（仕入値＋固定費＋送料）÷（1 − 手数料率 − 利益率）。売れたら +1%、14 日売れなければ 1 段下げる、値上げ後に売れなければ前の値段へ戻す、売れた直後 3 日は下げない。BR・TW・Japan Court（PH 1 店目）・PH2・MY2・SG2・JOOM が対象（PC で動いている 6 店＋JOOM。SG2 の設定は GitHub の main にまだ入っておらず、別の枝（feature/pricing-profit-rate）にだけある）。
- ライバル追随：front_list に人が URL を貼る → Claude が基準の色・サイズを選び、ライバルのページを Sonnet が見る → 「ライバル − 1 になる利益率」を商品ごとの例外として価格改定ツールに入れる（売れても上げない・売れなくても下げない。下限は空欄なら 0%、仕入値 2 万円以上は 5%。直近 14 日に売れた商品は今の率のまま止める。2026-10-13 決定）。**PH2 502 種類・MY2 540 種類に入っている。ブラジル・SG2・台湾・Japan Court は 0。**
- 価格改定モニター（状況・値上げ中・ライバル合わせ・要確認・ルール）。

**足りないもの（価格改定ツール Issue #23 の残り）**
1. **front_list → 価格改定ツールのつなぎは 10/13 に出来た**（front_list の「確定 OK」の行 → 店ごとの例外ファイル → PC の価格改定の置き場。PR #29・#30・#31、出品の道具 #43・#44）。**ただし PC で常駐しているループが古い版（9/29）のままで、例外ファイルを置いても拾わない。** ひろきが `Tools\ループを新しい版で起動し直す.bat` をダブルクリックする必要がある（Claude からは出来ない）。
2. ライバルの値段を取り直す定期の仕事は 10/14 に作った（毎週火曜 10:10・Sonnet・メインの Chrome・PC につながる設定あり。初回は 10/20）。まだ 1 回も動いていない。
3. 台湾の古い仕組み（rivals 65 件）の廃止と、PH2・MY2 の行に「確定 OK」が入っているかの確認。
4. **ブラジルのライバルが 1 件も紐づいていない**。リサーチDB の「BR_自店舗」（自店とライバル商品の ASIN のつなぎ）から Claude が候補を front_list に足し、人が確定 OK を付ける。**10 月末の手数料 6% → 18% 切り替えの前に済ませる**（切り替えで全商品が値上がりするため）。
5. ブラジルの手数料切り替え（10 月末）：切り替える日に、変わる値段の一覧を見せてから手数料率を 18% にする。
6. SG2 の設定を GitHub の main に入れる（今は PC と別の枝にだけある）。

### ④ 反応を見る
**今あるもの**
- 商品の反応（表示・クリック・いいね・カート・注文）を週 1 でセラーセンターから読んで GitHub に残す道具（bi_perf）。段階 A〜E の振り分けの決まりは手順書 50。
- 違反・順位下げの点検と、カテゴリの付け替え（API だけで動く。道具は出品の道具の violations.py、手順は手順書 60）。付け替えの実績はブラジルだけ（10/2・10/5・10/6）。

**足りないもの**
1. **反応の保存が実際には止まっている**（BR は 10/1、PH2 は 10/3 が最後。ほかの店は 0 回）。原因：この仕事はセラーセンターの画面を Chrome で読むが、週 1 の定期タスク（火曜 9:21）に PC につながる設定が無く、10/13 も 48 秒で何もせず「成功」で終わった。同じ定期の中の違反の点検（API だけで動く分）も 10/13 は動いていない。**直し方：この定期タスクを「この PC を必要とする」設定で作り直す**（新しい道具は作らない）。
2. 反応 → 次の行動がつながっていない。段階ごとの行動を決め（下の表）、週 1 の仕事の中で Claude が実行・提案する。

| 段階（手順書 50） | 行動 | 誰が |
|---|---|---|
| 売れた | 値上げ（+1%） | 価格改定ツール（自動・済み） |
| カート・いいねはあるが売れない | 値下げ（14 日で 1 段。自動・済み）→ 2 週たっても売れなければ **front_list にライバル候補の行を足す**（人が確定）＋仕入れ先を調べる対象に入れる | Claude |
| 表示はあるがクリックが少ない | 値段ではなく露出・画像の問題。広告の候補に入れる（カタログの文字は触らない：BAN の経験則） | Claude が候補を返事で出す |
| 表示がほぼ無い | 削除候補 → ⑤ へ | Claude が一覧、人が OK |
| 他店の売れ筋と一致している物 | 反応が弱くても消さない | Claude（リサーチDB と照合） |

### ⑤ 直す・消す（入れ替え）
**今あるもの**：出品中の全商品を API で取る道具（shop_items）、段階を付けて削除候補を出す道具（bi_perf replace）、API で削除する道具。BR で 10/2 に 1 回だけ実施。
**足りないもの**：週 1 で回っていない。④ の週 1 の仕事の最後に「削除候補の一覧」を返事で出し、OK が出た分だけ消し、空いた枠を ① の候補で埋める。

### ④-2 違反報告・順位下げ（2026-10-14 に段として追加）
**今あるもの**
- 削除・停止された理由を API で読む道具（violations.py scan）、送った後の点検（check）、カテゴリ違いの順位下げを Shopee の勧めるカテゴリへ付け替える道具（fix-category）。手順は手順書 60。実績：理由の読み取りは BR・PH2・TW・MY2、付け替えは BR だけ。
- 異議申し立ての型と記録：ec-knowledge の `Shopee/50_ペナルティと異議申し立て.md`（BR LSR は 10/13 承認、MY NFR は結果待ち、MY の知的財産 2 点は 10/26 期限）。

**足りないもの**
1. 週 1 で回っていない（④ と同じ定期に入っているが止まっている）。④ の定期を作り直す時に、違反の読み取り → 順位下げの付け替え → 申し立てが要る物の一覧、を同じ 1 本に入れる。
2. 申し立ては道具が無く、セラーセンターで人が送る（500 文字まで）。**Claude が文面と期限の一覧を返事で出し、ひろきが送る。結果は ec-knowledge 50 に Claude が記録する**（人が決める事の 7 つ目として、下の §1 に足す）。
3. 出品中の全件で今のカテゴリと推奨を比べる先回りの見直しは、まだ案の段階（手順書 60）。順番は後。

### ⑤-2 ショップカテゴリ・店の見た目（2026-10-14 に段として追加）
**今あるもの**：全店とも公式 API で棚分けする道具（shop_category.py。決まりは店ごとの設定ファイル config/shops/<店>.yaml）。実績：BR 10/3、PH2・MY2・SG2 10/9。店トップの飾り（バナー・ブランド一覧）は Chrome でセラーセンターを操作し、下書きまで Claude、公開はひろき（手順書 10）。

### ① 何を出すか（売れ筋リサーチ）
**今あるもの**
- 強い競合店の Top Sales（月 1）・新着（週 1）を拡張機能のコードで取ってリサーチDB の「商品リスト」を更新する道具。**runner は全部の国に対応**。リサーチDB には既に PH 417 店・4,060 商品（最後の取得 9/17）、MY・SG・TW・TH も入っている。

- 出品候補の見やすいシート（BR_売れ筋・BR_自店舗・BR_出品候補・BR_新着の 4 タブ。数式）。

**足りないもの**
1. **BR 以外で定期が回っていない**。定期タスクはブラジルの行だけを読んでいる。seller list の国の列で店を選ぶ形にして、全店で同じ 2 本（月 1・週 1）を回す。

### ② 出す
**今あるもの**：出品の道具（catalog-listing。Shopee 全店・JOOM で 1 本）。下準備 → 文章 → 画像 → 確認ページ → OK → 送信 → 15 分後点検 → 価格改定の対象に登録。MY2・SG2・PH2 向けの候補 58 カタログが絞り込み済み。
**足りないもの**
