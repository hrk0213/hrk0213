# 店の売上と利益の要 — 一気通貫の設計（2026-10-13 作成・Fable）

人（ひろき）の判断を AI に落とし込み、「何を出す → 出す → 値段 → 反応を見る → 直す・消す」の 1 周を、Shopee の全店と JOOM で同じ道具・同じ表で回すための設計。
各道具の細かい手順は各リポジトリの正本にある。ここは**全体の形と、人が決める所と、作る順番**だけを書く。変えたら同じ日にここを直す。

## 0. ゴールと考え方

- ゴール：**利益の合計を増やす**（利益率ではなく合計。2026-09-30 決定）。
- 店が強くても値段が高ければ売れない。だから要の順番は **③ 値段 → ④ 反応 → ⑤ 直す・消す → ① 何を出す → ② 出す**（2026-10-13 ひろきさん：ライバル追随と価格調節が最優先）。
- 原則（全部、ひろきさんの既決）
  1. 道具も表も**全店共通**。店の違いは「店の列」か「店ごとの設定ファイル」だけ。店ごとに別の表・別のタブ・別のスクリプトは作らない。
  2. **人が決める所は、決まった表の決まった列**にだけ書く。Claude はその表を毎回読んで動き、結果を**同じ表**か今あるモニターに書く。新しい見る場所は作らない。
  3. 人が覚える事（スキル名・定型文の名前・列の記号）を前提にしない。頼み方は日本語の一言。
  4. 店に送る前は完成形を見せて OK（新規出品・作り直し・値段の付け直し）。日々の自動の値段の上げ下げだけは、決めたルールの範囲で自動。
  5. 送った後は必ず点検（削除・BAN・順位下げ）。

## 1. 人が決める事は 6 つだけ（それ以外は Claude）

| # | 決める事 | 書く場所 | いつ |
|---|---|---|---|
| 1 | どの自店商品を、どのライバルと比べるか（ライバルの URL） | front_list（スプレッドシート「フロント商品・改善商品リスト」）の rival_url 列。**Claude が候補の行を足し、人は確定 OK を付けるだけ**にする（下の ③） | 週 1 の報告を見た時 |
| 2 | その商品をどこまで追いかけるか（下限の利益率。空欄＝0%） | front_list の「下限の利益率」列 | 同上。0% より下はここに書いた時だけ |
| 3 | 新しく出す候補を出すか出さないか | 出品待ちの表（リサーチDB に 1 タブ。全店共通。下の ①）の「人の可否」列。Shopee は当面すべて人が OK、JOOM は自動 | 週 1 の報告を見た時 |
| 4 | 売れない物を消すか | Claude が一覧を返事で見せ、OK を返す（表は作らない） | 週 1 |
| 5 | ブランド・商品のルール（この国でこのブランドは出さない、など） | 出品の道具の config/brand_policy.yaml・knowledge/restrictions.yaml（Claude が書く。人は返事で答えるだけ。同じ事を二度聞かない） | 聞かれた時 |
| 6 | 値段の基本ルール（利益率のスタート・下限・何日売れなければ下げる・手数料率） | 価格改定ツールの pricing_rules.json（Claude が書く）。見るのは価格改定モニターの「ルール」 | 変えたい時 |

## 2. 五つの段（今あるもの・足りないもの）

### ③ 値段（最優先）
**今あるもの**
- 価格改定ツール（PC で毎日）：式 ＝（仕入値＋固定費＋送料）÷（1 − 手数料率 − 利益率）。売れたら +1%、14 日売れなければ 1 段下げる、値上げ後に売れなければ前の値段へ戻す、売れた直後 3 日は下げない。BR・TW・PH2・MY2・SG2・JOOM が対象。
- ライバル追随：front_list に人が URL を貼る → Claude が基準の色・サイズを選び、ライバルのページを Sonnet が見る → 「ライバル − 1 になる利益率」を商品ごとの例外として価格改定ツールに入れる（売れても上げない・売れなくても下げない・下限は 0%）。**PH2 502 種類・MY2 540 種類に入っている。ブラジル・SG2・台湾・Japan Court は 0。**
- 価格改定モニター（状況・値上げ中・ライバル合わせ・要確認・ルール）。

**足りないもの（価格改定ツール Issue #23）**
1. **front_list → 価格改定ツールが直接つながっていない**。今は Claude がその場で計算して設定ファイルに書いている。「front_list に行を足して確定 OK を付ければ、どの店の商品でも自動で追いかける」形にする（2026-10-12 決定）。
2. **ライバルの値段を取り直す定期の仕事が無い**（10/9 に 1 回見ただけ。次の予定なし）。週 1 で取り直し、率を直す。取り方は手順書 45 の通り（メインの Chrome・10〜25 秒間隔・本人確認が出たら止める）。
3. **ブラジルのライバルが 1 件も紐づいていない**。リサーチDB の「BR_自店舗」（自店とライバル商品の ASIN のつなぎ）から Claude が候補を front_list に足し、人が確定 OK を付ける。**10 月末の手数料 6% → 18% 切り替えの前に済ませる**（切り替えで全商品が値上がりするため）。
4. ブラジルの手数料切り替え（10 月末）：切り替える日に、変わる値段の一覧を見せてから手数料率を 18% にする。

### ④ 反応を見る
**今あるもの**
- 商品の反応（表示・クリック・いいね・カート・注文）を週 1 でセラーセンターから読んで GitHub に残す道具（bi_perf）。段階 A〜E の振り分けの決まりは手順書 50。
- 違反・順位下げの点検と、カテゴリの付け替え（違反は API で動いている）。

**足りないもの**
1. **反応の保存が実際には止まっている**（BR は 10/1、PH2 は 10/3 が最後）。原因：この仕事はセラーセンターの画面を Chrome で読むが、毎週の定期タスクはクラウドで動くので PC の Chrome に届かず、何もせず「成功」で終わっている。**直し方：定期タスクを「この PC を必要とする」設定で作り直す**（新しい道具は作らない）。
2. 反応 → 次の行動がつながっていない。段階ごとの行動を決め（下の表）、週 1 の仕事の中で Claude が実行・提案する。

| 段階（手順書 50） | 行動 | 誰が |
|---|---|---|
| 売れた | 値上げ（+1%） | 価格改定ツール（自動・済み） |
| カート・いいねはあるが売れない | 値下げ（14 日で 1 段。自動・済み）→ 2 週たっても売れなければ **front_list にライバル候補の行を足す**（人が確定）＋仕入れ先を調べる対象に入れる | Claude |
| 表示はあるがクリックが少ない | 値段ではなく露出・画像の問題。広告の候補に入れる（カタログの文字は触らない：BAN の経験則） | Claude が候補を返事で出す |
| 表示がほぼ無い | 削除候補 → ⑤ へ | Claude が一覧、人が OK |
| 他店の売れ筋と一致している物 | 反応が弱くても消さない | Claude（リサーチDB と照合） |

### ⑤ 直す・消す（入れ替え）
**今あるもの**：出品中の全商品を API で取る道具（shop_items）、段階を付けて削除候補を出す道具（bi_perf replace）、API で削除する道具。BR で 10/2 に 1 回だけ実施。
**足りないもの**：週 1 で回っていない。④ の週 1 の仕事の最後に「削除候補の一覧」を返事で出し、OK が出た分だけ消し、空いた枠を ① の候補で埋める。

### ① 何を出すか（売れ筋リサーチ）
**今あるもの**
- 強い競合店の Top Sales（月 1）・新着（週 1）を拡張機能のコードで取ってリサーチDB の「商品リスト」を更新する道具。**runner は全部の国に対応**。リサーチDB には既に PH 417 店・4,060 商品（最後の取得 9/17）、MY・SG・TW・TH も入っている。
- 自店とのつなぎ（research_own_link）、強いブランドの新製品ウォッチ（brand_watch）、売れた物から広げる縦・横（research/seeds・expand。JOOM で週 1 稼働）。
- 出品候補の見やすいシート（BR_売れ筋・BR_自店舗・BR_出品候補・BR_新着の 4 タブ。数式）。

**足りないもの**
1. **BR 以外で定期が回っていない**。定期タスクはブラジルの行だけを読んでいる。seller list の国の列で店を選ぶ形にして、全店で同じ 2 本（月 1・週 1）を回す。
2. **BR_ の 4 タブを店ごとに増やす形は不可**（2026-10-07 ひろきさん）。4 タブを **1 つの「出品待ち」タブ**（店の列・候補・理由と点数・出典・人の可否・状態）にまとめ、全店をここに流す。JOOM の「出品待ちの列」（2026-10-06 決定）と同じ考え方。
3. 定期タスクは Chrome が要るので、④ と同じく「PC を必要とする」設定で作り直す。

### ② 出す
**今あるもの**：出品の道具（catalog-listing。Shopee 全店・JOOM で 1 本）。下準備 → 文章 → 画像 → 確認ページ → OK → 送信 → 15 分後点検 → 価格改定の対象に登録。MY2・SG2・PH2 向けの候補 58 カタログが絞り込み済み。
**足りないもの**
- JOOM の毎日の自動出品：「Keepa の商品紹介を説明文に使う」段を 2026-10-13 に手順書と道具に足した（Keepa は使えれば使う。無くても Amazon の説明で書いて止まらない）。同じ日に、種類名に型番・型番ごとの寸法の行・JOOM の属性も決めた（出品リポジトリ Issue #36）。**残り：試しの 3 カタログをひろきさんが見て OK → 定期タスクを再開**。
- Shopee の新規は人の OK を毎回取る（決まり）。「出品待ち」タブで人が可否を付けた物だけを出す形にすれば、確認ページの OK と二重にならない（確認ページは完成形の確認、タブは出す・出さないの判断）。

## 3. 週の回し方（全店共通）

| いつ | 何 | 動き方 |
|---|---|---|
| 毎日 | 値段の上げ下げ・在庫・判断待ちの知らせ | 価格改定ツール（自動・済み） |
| 毎日 8:00 | JOOM の自動出品（Keepa の段を足してから再開） | 定期タスク |
| 毎週月曜 | 強い店の新着・強いブランドの新製品 → 「出品待ち」タブに足す（全店） | 定期タスク（PC 必要） |
| 毎週火曜 | ④ 反応の保存 → 段階 → 行動（値下げは自動、ライバル候補を front_list に、削除候補と広告候補を返事で） → ⑤ OK が出た分を削除 → 空いた枠に ① の候補 | 定期タスク（PC 必要）＋人の OK |
| 毎週（火曜の中で） | ライバルの値段の取り直し → 率を直す → モニターの「ライバル合わせ」に反映 | 同上 |
| 毎月 1 日 | Top Sales の取り直し（全店） | 定期タスク（PC 必要） |
| 10 月末 | ブラジルの手数料 18% 切り替え（一覧を見せてから） | Claude |

人が見るのは **3 か所だけ**：価格改定モニター（値段の状態）・front_list（ライバル）・リサーチDB の「出品待ち」タブ（候補）。それ以外は返事で見せる。

## 4. 作る順番（利益に近い順。ブラジルで仕上げ → フィリピンへ）

1. **ライバル追随の共通化**（価格改定ツール #23）：front_list の確定 OK の行を直接読む／週 1 の取り直し／PH2・MY2 の今の設定をこの形に移す。→ 担当：Opus（コード）・Sonnet（見に行く）。
2. **ブラジルのライバル候補出し** → front_list に足す → 人が確定 → 1 の仕組みで動かす。10 月末の手数料切り替えより前。
3. **④⑤ の週 1 を本当に動かす**：PC 必要の設定で定期を作り直し、段階 → 行動のつなぎを入れる。まずブラジルで 1 周回して結果を見せる。
4. **① の全店化**：「出品待ち」タブを作って BR_ 4 タブを畳む。PH の店を月 1・週 1 の対象に入れる（セラー 417 店は既にある）。
5. **フィリピン（PH2）に当てる**：2〜4 をそのまま PH2 で回す。合わせて MY2・SG2・PH2 の候補 58 カタログの出品を再開（人の OK）。
6. **JOOM の自動出品を再開**：Keepa の段を手順と定期に足す → 1 日 100 で再開。約 110 件の作り直しは GPT が続ける（ぶつからないよう、新規は自動出品、作り直しは GPT と分ける）。
7. その後：仕入れ先を Amazon 以外にも（#27）・広告。
